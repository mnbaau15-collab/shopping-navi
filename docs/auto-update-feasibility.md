# 課題：stores.js の店舗情報を、自動更新する仕組みは作れるか

## 結論（先に）

**「確認が必要なところを、自動で見つけて知らせる」仕組みは作れる（試作ずみ）。**
**「お店のページから情報を読み取って、stores.js を自動で書き換える」仕組みは、技術的には作れるが、採用しなかった。**
理由は、規約・正確さ・利用者への影響の3つ。

## 1. 自動化できる範囲

| 項目 | 自動でできること | 自動で書き換えてよいか |
|---|---|---|
| データの形（必須項目・idの重複・範囲外の位置・読みがなの形） | ◎ 検査できる | － （直すのは人） |
| 公式ページのURL | ○ 開けるかを、1軒1回だけ調べられる（404・移転・証明書の問題など） | ✕ 新しいURLは、人が確かめて直す |
| 確認日（updatedAt）の古さ | ◎ 「半年以上、確認していない」お店を見つけられる | － |
| 営業時間・住所・店名の変更 | △ お店のページを読み取れば、技術的には可能 | ✕ **採用しない**（下の理由） |
| 位置（緯度・経度） | ○ 住所が変われば、国土地理院の検索で候補は出せる（今回、最初の登録で使った） | ✕ 候補は、人が地図で確認してから登録する（候補が最大で約1.4km ずれていた） |

## 2. 作ったもの（試作）

- `tools/check-stores.js`：Node.js（ライブラリなし）。
  - 通常：データの形だけを検査（ネットにはつながない）
  - `--links`：各お店のURLが開けるかを、**1軒1回・1.5秒おき**に確認（ページの中身は読まない）
  - `--report`：結果を、文章のファイルにする
- `.github/workflows/check-stores.yml`：GitHub Actionsで実行する設定。**いまは手動実行だけ**にしてあり、`schedule` の3行の `#` を外すと、**毎週月曜**に自動で動く。問題があれば、**Issue（やることリスト）を自動で作る**。
- 動作確認：本物の `stores.js`（エラー0件）、壊れたデータ（エラー6件を検出）、手元の模擬サーバー（正常・移転・404・503・無応答・接続不可を判定）。

自動更新の流れは、「**自動で見つける → 知らせる → 人が確認して直す → コミット**」。

## 3. 「ページを読み取って自動で書き換える」を採用しなかった理由

1. **規約**：トクバイの規約は、通常を超えるアクセスや、機能の解析を禁止している（第14条5・7号）。アプリに組み込むと、利用者が使うたびにアクセスが起きる。
2. **ブラウザの制限**：公開ページ（ブラウザのJavaScript）から、別サイトのページは読めない（CORS）。読むには、自前のサーバーが必要になり、構成が大きくなる。
3. **正確さ**：ページの作りが変わると、すぐに壊れる。間違った営業時間などが公開ページに出ると、**閉まっているお店に、高齢の利用者が行ってしまうおそれ**がある。
4. **方針**：このアプリでは「情報は、人が公式サイトで確認して登録する」「他サイトから自動取得しない」と決めている（CLAUDE.md）。
5. **内容の再利用**：他社のチラシ情報を、自分のアプリに取り込むことになる。リンクで案内するほうが、安全。

## 4. 今後の改善案

- 各お店に `updatedAt`（確認日）を入れて、再確認の知らせが出るようにする。
- お店に、「チラシのページへ、リンクしてよいか」を確認する。
- 営業時間などを増やすときも、**自動取得ではなく、公式ページを見て手で登録**し、確認日を記録する。
- 規約が許す、公式のデータ提供（API・オープンデータ）があれば、そちらを使う。

## 5. 説明の一言

> 「自動更新は、『見つけて知らせる』までを自動にして、書き換えは人が確認してから行う形にしました。ページを読み取って自動で書き換える方式は、規約と正確さの面から採用しませんでした。」
